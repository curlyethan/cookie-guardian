Why Cookie AutoDelete stopped working — and where its 100,000+ users went

In late 2024, every Cookie AutoDelete user got the same Chrome warning: "This extension is no longer supported." Days later, the icon was gone. Here's what actually happened, why the maintainer didn't migrate it, and what came next.

Last updated: 8 May 2026

What happened — the timeline

The end of Cookie AutoDelete (CAD) on Chrome wasn't sudden. It was the end-state of a six-year platform transition that the Chromium team had been signposting since 2018. Here's the sequence, anchored to the events that mattered for end users:

  • 2018 — Chromium team publishes initial Manifest V3 design proposals, beginning a multi-year discussion with extension developers about the new platform's blocking-API restrictions.
  • December 2022 — Cookie AutoDelete ships its last release: v3.8.2. After this point, the project enters maintenance limbo, with infrastructure-only commits but no shipped feature work. (verified via the project's GitHub release page)
  • 2023 — Google formally re-publishes the MV2 deprecation timeline after several delays, naming concrete dates for enforcement.
  • June 2024 — Chrome stops accepting new MV2 extension submissions in the Chrome Web Store. Updates to existing MV2 listings are restricted.
  • Late 2024 — Chrome begins disabling MV2 extensions for users on the Stable channel in waves. CAD users start seeing "this extension is no longer supported" notices and the toolbar icon greys out.
  • Through 2025 — The CAD GitHub repository sees occasional dependency-bump commits (last activity: April 2025) but no MV3 rewrite. The community-fork project median-dxz/Cookie-AutoDelete-MV3 publishes early MV3 builds outside the Chrome Web Store.

If you're reading this and your CAD icon is still working, you're almost certainly on Firefox — Mozilla retained MV2 support past Chrome's cutoff, and the Firefox add-on listing for CAD continues to function on that browser as of writing.

What Manifest V3 actually changed (technically)

To understand why Cookie AutoDelete couldn't simply ship an "MV3 update," it helps to see what MV3 actually changed under the hood. Four shifts mattered the most for cookie-management extensions:

1. The death of blocking webRequest

In Manifest V2, an extension could intercept any network request, inspect it, and synchronously block or modify it:

// MV2 — persistent background page
chrome.webRequest.onBeforeRequest.addListener(
  callback,
  { urls: ['<all_urls>'] },
  ['blocking']
);

In MV3, the 'blocking' mode of onBeforeRequest is unavailable to non-enterprise extensions. The replacement is declarativeNetRequest — instead of running JavaScript on every request, the extension pre-declares static rule sets that the browser evaluates internally. There is a hard ceiling: roughly 30,000 dynamic rules per extension, plus stricter ceilings on session rules. For an extension that needs per-tab cookie tracking with millions of possible domain combinations, that limit is unworkable without a redesign.

2. Service workers replace persistent background pages

MV2 extensions could run a persistent background page that lived for as long as the browser was open. CAD used this to hold an in-memory map of which domains had which cookies in which tabs — a lookup table that needed to survive across page navigations and tab events.

MV3 replaces this with a service worker: the extension's background script runs only when needed and is terminated by Chrome after roughly 30 seconds of inactivity. State that used to live in memory now has to be persisted to chrome.storage.session (volatile across browser restarts) or chrome.storage.local (slower, with quotas), and re-hydrated on every wake. Architecturally this is closer to a stateless function than a long-running daemon.

3. Stricter content security policy

MV3 forbids remotely-hosted code, inline event handlers, and eval() in extension contexts. For most cookie tools this is a non-issue — but extensions that bundled older libraries or used dynamic code generation needed cleanup before they could even load under MV3.

4. Promises everywhere

Most callback-style Chrome APIs were re-issued as Promise-returning equivalents, and several MV2 callback patterns were deprecated. Existing MV2 codebases work, but a clean MV3 rewrite typically modernises the entire async surface — another non-trivial chunk of work.

None of these changes individually killed cookie-management extensions. The combination did. CAD's architecture relied on a persistent background page tracking tab state across long sessions — and that pattern simply does not exist in MV3. A migration was a redesign, not a port.

Why this hits cookie tools harder than ad blockers

It's worth being precise about why cookie-management extensions specifically struggled with MV3, because the most-cited MV3 casualty narrative is the ad-blocker one. Ad blockers and cookie cleaners look superficially similar — both intercept site behaviour for privacy reasons — but the architectural mismatch with MV3 is different in each case.

Ad blockers fight a rule-count battle: declarativeNetRequest's 30,000-rule ceiling is a constraint relative to community block lists that ship hundreds of thousands of rules. The fight is over how many rules an extension can declare. Cookie auto-deleters, by contrast, fight a state-tracking battle: there isn't really a "rule" for "delete the cookies for example.com when the last tab pointing at example.com closes." That's an event-driven, stateful operation that needs to know which tabs exist, which domains they belong to, and when a tab-close event leaves zero remaining tabs for a given domain. Persistent in-memory state was the natural way to do that under MV2; under MV3 it has to be reconstructed from chrome.storage on every service-worker wake-up, with all the latency and quota tradeoffs that implies.

Why CAD specifically couldn't migrate

Several MV2 extensions did ship MV3 versions. uBlock Origin Lite — Raymond Hill's MV3-compatible cousin to uBlock Origin — was published in 2022 and continues to ship. AdGuard, 1Password, LastPass, and Bitwarden all migrated. So why not CAD?

Three structural reasons, drawn from the project's own GitHub history:

  • Volunteer maintainer bandwidth. CAD was led primarily by a single GitHub user (kennethtran93) with help from a small handful of contributors. Public commit activity tapered through 2023 and continued tapering through 2024, with the most recent commits in 2025 being dependency bumps from Dependabot rather than feature work.
  • The MV3 migration was a redesign, not a port. CAD's persistent-background-page architecture mapped poorly onto service workers. Greylist expiry timers, per-tab cookie tracking, and the "cleanup on tab close" event handler each needed re-thinking, not re-typing. Estimated effort in community discussion was several hundred hours of focused work.
  • No commercial support. uBlock Origin Lite has Raymond Hill's full-time maintainer attention; AdGuard has a paid team; the password managers are commercial products. CAD was an unpaid project with a small contributor base. Sustaining a multi-month rewrite with no funding, while the MV2 version still worked for a few more years, was a hard ask.

The result: as discussed in the project's GitHub issue tracker through 2023 and 2024, the MV3 rewrite was scoped, debated, and ultimately not shipped in time. Existing forks — most notably median-dxz/Cookie-AutoDelete-MV3 — published partial MV3 ports but did not pass through the Chrome Web Store review process, leaving the official Web Store listing as the casualty when MV2 was disabled.

The wider pattern. Of the MV2 extensions disabled in the late-2024 enforcement wave, the survivors broadly fell into two camps: well-funded commercial products and single-purpose extensions whose feature set fit cleanly into declarativeNetRequest rules. Volunteer projects with stateful, event-driven architectures — exactly CAD's shape — were over-represented in the casualties.

Where the 100,000+ users went

CAD's Chrome install base before delisting was widely cited at 100,000+ users (per the Chrome Web Store user-count badges). That cohort didn't disappear — they redistributed across a small set of options. Roughly, in order of where the migration traffic visibly went:

  • Purpose-built MV3 replacements. A small set of MV3-native cookie cleaners filled the post-CAD vacuum. The closest like-for-like replacement — auto-delete on tab close, whitelist, greylist, cookie aging — is Cookie Guardian, which has accumulated an active user base and a Featured-by-Chrome listing since launch. The full landscape comparison lives on the alternatives page.
  • Cookiebro. Pre-existing MV3-compatible extension that picked up a chunk of the CAD diaspora. Stronger on cookie-editor power-user features; weaker on the close-a-tab-and-forget-it default behaviour.
  • Chrome's built-in "clear on exit." Chrome has a native setting to delete cookies when all browser windows are closed, with a per-site whitelist. For users who fully quit Chrome regularly, this is enough; for users who keep Chrome open for days at a time, it almost never fires.
  • The Firefox migration. A non-trivial slice of the CAD user base moved to Firefox specifically to keep CAD running. Mozilla retained MV2 support, and CAD's Firefox listing continues to receive updates from the same project.
  • The long tail: nothing. Some users simply stopped replacing CAD and now live with persistent cookies, accepting the loss. This was visible in subreddit threads through early 2025 — users asking "what should I use instead?" and a smaller fraction explicitly saying they'd given up on a replacement.

What this means for browser extension trust

Zoom out and CAD's end is a case study in a structural truth about browser extensions: they are tenants on a platform, and platforms re-architect. Users who depended on CAD discovered, in the space of a few weeks in late 2024, that their privacy workflow had a single point of failure they hadn't priced in — the willingness of one volunteer maintainer to re-write the project on the platform's new schedule.

That isn't an indictment of CAD or of Chrome. It's a property of the model. A few practical lessons fall out of the transition:

  • Built MV3-native from day one matters. Extensions designed against the current platform — service workers, declarative rules, modern storage APIs — are structurally less likely to be next on the deprecation list. There will be MV4 eventually, but greenfield MV3 code is closer to wherever the platform goes next than retrofitted MV2 code is.
  • Maintenance posture matters more than feature count. A simple extension that ships an update every quarter is more reliable than a feature-rich one whose last release was three years ago. When auditing a privacy extension, look at the release cadence first.
  • Open about the dependency footprint. Cookie tools that explicitly document which Chrome APIs they rely on — and which would force a rewrite if deprecated — are easier to evaluate. Privacy tooling deserves the same supply-chain hygiene that backend infrastructure already has.

None of this changes the verdict for CAD itself, which remains a well-loved and well-built MV2-era project that simply ran out the clock. It does change the questions worth asking about whatever you replace it with.
